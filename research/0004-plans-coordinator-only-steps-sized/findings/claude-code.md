## Summary

- The Agent tool takes `model` (enum `sonnet|opus|haiku|fable`, aliases only, no `[1m]`) and `effort` (`low..max`); a custom agent's frontmatter has `model` and `effort`. A subagent's window is set by its own model, not chosen per step: on Opus/Sonnet/Haiku 5.x it is 1M by default, 200k only via global `CLAUDE_CODE_DISABLE_1M_CONTEXT=1`.
- `/clear` keeps the session's effort (hal2's log shows the screen at `max` after a clear). The `max -> medium` change the user saw is hal2's autoclear: `~/.config/hal2/agents.toml` has `[autoclear] effort = "medium"`, so it types `/effort medium` after every clear.
- `/effort <level>` (not `max`) rewrites `modelSettings.<model>.effortLevel` in settings.json, so one session's change leaks into every new session; `max` and `s` in the slider are session-only.
- A script reads effort from `$CLAUDE_EFFORT` (Bash tool env), the statusline/transcript, and the model/window from the statusline JSON (`model.id`, `context_window.context_window_size`); hooks give `effort` only on tool-use events.
- A subagent keeps its own window; only its final report lands in the parent. Finished subagents resume with `SendMessage` (history kept); `/clear` resets the name check, so persist agent ids in plan files.

## Answers

1. **Agent `model` values.** Tool schema in this session's transcript: `"model" enum ["sonnet","opus","haiku","fable"]`, "takes precedence over the agent definition's model frontmatter ... ignored for `fork`: forks inherit the parent model". Order (SUB, "Choose a model"): per-invocation `model` > frontmatter `model` (`inherit` = parent) > `CLAUDE_CODE_SUBAGENT_MODEL` (since v2.1.251; `_FORCE=1` forces) > parent's model. Frontmatter accepts `sonnet|opus|haiku|fable`, a full id (`claude-opus-5-5`) or `inherit`; `[1m]` is not listed as a frontmatter value. A family alias equal to the parent's family "runs on the main conversation's exact model, including any `[1m]` suffix" (SUB). Window: "sized by its own model, not the parent's" (SUB). MODEL: Opus 4.7+/Sonnet 5+/Haiku 5.5/Fable run 1M by default, Opus/Sonnet 4.6 only via `[1m]`; `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` holds all to 200k (global, hits the coordinator too). So a per-step "200k vs 1m" choice does not exist as a parameter; it is a model choice (4.6 models) or a budget the step sizes itself to. Confidence: high for the enum and order (doc + schema), medium for "full id with `[1m]` in frontmatter" (undocumented; test with `claude --agents`).
2. **Agent `effort` and frontmatter.** Schema: `effort enum low|medium|high|xhigh|max`, "Set this ONLY when the user or instructions (CLAUDE.md, a skill) explicitly ask ... Ignored for fork: a fork runs at your own effort". SUB ("Choose an effort level", v2.1.292+): the parameter overrides the definition's `effort`, stays in effect on resume; `CLAUDE_CODE_EFFORT_LEVEL` beats both; frontmatter `effort` exists ("Overrides the session effort level, but not the env var"). Levels depend on the model. Local proof: `subagents/agent-*.meta.json` of this subagent records `"model":"sonnet","effort":"high"` while the parent runs at `max`: the parent passed `effort`, a subagent does not inherit the parent's `max`. Confidence: high.

5. **Subagent context.** Own window; "does that work in its own context and returns only the summary" (SUB); a fork shares the parent's cache and "only its final result comes back". Only the report (completion notification) counts against the parent, plus the Agent call itself; non-fork subagents start fresh and see only the prompt, CLAUDE.md and git status. `SendMessage` with agent id or name resumes a completed subagent in the background, history kept (SUB). Transcripts: `~/.claude/projects/<project>/<session>/subagents/agent-<id>.jsonl` (+ `.meta.json`). `/clear`: SUB says the SendMessage name-to-agent check "resets on /clear"; what happens to a running subagent is not documented (my inference: they are tied to the session id, plan not to rely on them). Confidence: high for context, low for /clear survival (untested).

## Implications for the plan skill

- Pass `model` and `effort` on every step's Agent call (the schema says to set `effort` only when instructed, so the plan skill's rule in SKILL.md counts as that instruction); do not rely on inheritance, and never set `CLAUDE_CODE_EFFORT_LEVEL`.
- "Window" is not a parameter. Record it as a budget: size each step under 35% of the window of the step's model (1M for 5.x models; 200k only if the user pins an `[1m]`-less 4.6 model or `CLAUDE_CODE_DISABLE_1M_CONTEXT`), and give the subagent a `maxTurns` and a "report under N lines" rule. A 200k-sized step runs fine on a 1M model, so the 200k/1m column can be a sizing label, not a launch option.
- Per-step effort in a plan table: use the Agent `effort` parameter; a sensible default is the step's own column, with `max` allowed (it is session-only and never written to settings).
- Coordinator identity across handoff+clear: `/clear` itself keeps model and effort. What breaks it is hal2 autoclear's `[autoclear] effort = "medium"` (it types `/effort medium`, which also rewrites `modelSettings` in settings.json for every new session). Fix options: change or empty that key, or let the handoff record the level and hal2 type that level back (`/effort max` is session-only, so it also stops leaking). The `/handoff` file should record model, effort, window read from the live session (below).
- Reading the live state in a skill script: effort from `$CLAUDE_EFFORT`; model from the last `Set model to` in the transcript, else the `claude` process `--model`, else `$ANTHROPIC_MODEL`, else settings (what `context.py` does); window from `[1m]`/"1M context" or, better, a statusline-written cache holding `context_window_size` and `model.id`. Do not use `message.model` from the transcript for the window.
- Resume instead of relaunch: keep each step's agent id/name in the plan folder; `SendMessage` continues a finished step with its history and its model/effort (they persist on resume), but treat survival across `/clear` as unproven and fall back to a fresh Agent call with the same model/effort.
- Unverified, to test before relying on it: `model: opus[1m]` in a frontmatter or `--agents` JSON; whether a running background subagent survives `/clear`; `/model` mid-session reaching an `inherit` subagent (MODEL says `/model` switches reach inheriting subagents).
- No official docs page covers "coordinator-only"; use `/feedback` for a request such as a per-invocation window parameter.
